# Platform Architecture

This document describes how Kairon handles platform-aware evidence processing without a Windows-first control flow.

## Platform Detection

`backend/app/core/evidence_platforms.py` is the single backend entry point for platform identity.

- `detect_evidence_platform()` infers `windows`, `linux`, `memory`, `mixed`, `macos`, or `unknown` from evidence type, extensions, and path heuristics.
- `resolve_evidence_platform()` turns provided and detected values into the persisted `effective_platform`.
- `detect_memory_os_hint()` keeps memory OS inference separate from the top-level evidence platform.

The persisted evidence fields remain:

- `provided_platform`
- `detected_platform`
- `effective_platform`

The API adds `platform_profile`, which is the UI-facing source of truth.

## Platform Registry

`PLATFORM_REGISTRY` in `backend/app/core/evidence_platforms.py` defines platform-level metadata:

- display label
- upload label/description
- support state

Platform capabilities are not hardcoded per screen. They are aggregated from the artifact registry using `build_platform_capabilities()`.

Examples:

- `supportsTimeline`
- `supportsSearch`
- `supportsRegistry`
- `supportsJournal`
- `supportsMemory`
- `supportsPackages`
- `supportsUsers`

For mixed evidence, capabilities are the union of all selected platforms.

## Artifact Registry

`backend/app/core/artifact_registry.py` is the central backend artifact-family registry.

Each artifact family declares:

- `id`
- `label`
- `platforms`
- `aliases`
- `category`
- `group_id` / `group_label`
- `icon`
- `parser`
- `normalizer`
- `view`
- `searchable`
- `timeline_capable`
- `severity_support`
- `usable_tier`
- `filter_fields`
- `quick_selects`
- `capabilities`

This registry is used to derive:

- platform capabilities
- platform UI groups
- platform quick selects
- artifact family metadata exposed to the frontend
- usable ingest tier membership

## Discovery Pipeline

The high-level evidence flow is:

Upload/Register
-> Extraction / folder inventory
-> Nested archive unwrap when needed
-> Evidence type detection
-> Artifact discovery
-> Parser dispatch
-> Normalization
-> Indexing
-> Search / Timeline / Artifact Views

Linux-specific discovery remains in `backend/app/ingest/linux/discovery.py`, but the output is normalized back into the shared platform-driven flow.

Important behaviors:

- Linux collections can be detected from collection heuristics, not only single files.
- Nested archives such as `tar.gz -> tar` are unwrapped during ingest.
- Host fallback can come from `hostnamectl.txt` when `/etc/hostname` is missing.

## Host Information

Normalized observations from Linux and Windows producers also feed a platform-agnostic Host Facts / Local Accounts layer, consumed by the per-host Host Information UI. See [host-information.md](../evidence/host-information.md) for the fact-type/platform coverage matrix, conflict resolution model, and what is and isn't decoded from the Windows SAM/ProfileList hives today.

## Parser Dispatch

Parser registration remains plugin-based in `backend/app/parsers/*` with explicit imports in `backend/app/parsers/__init__.py`.

Artifact-family metadata and parser metadata are separate concerns:

- artifact registry answers what a family is and how the UI should treat it
- parser registry answers how a parser behaves and what searchable contract it emits

`usable_ingest.py` consumes the artifact registry for artifact-tier decisions instead of maintaining platform-specific lists.

## Normalization

Normalization remains in the existing ingest normalizers.

The artifact registry records the intended normalizer for each family, but runtime normalization still follows the current parser/normalizer implementation path so behavior stays compatible.

## UI Registry

Frontend artifact presentation is centralized in:

- `frontend/src/lib/artifactRegistry.ts`
- `frontend/src/lib/platformRegistry.ts`

These files provide one UI-facing registry for:

- artifact labels
- alias resolution
- canonical artifact keys
- artifact view mapping
- platform upload options

Screens that previously carried local lists now read from the shared registry:

- Search
- Timeline
- Artifact Explorer
- Finding prefill helpers

Evidence Detail remains evidence-driven through `platform_profile`, which is generated by the backend from the platform registry plus artifact registry.

## Mixed Evidence

Mixed evidence is represented as:

- `effective_platform = mixed` when appropriate
- `platform_profile.platforms = [...]`
- `platform_profile.capabilities` as a union
- `platform_profile.groups` grouped by source platform

This allows future combinations such as:

- Windows + Memory
- Linux + Memory
- Windows + Linux

without introducing special-case UI branching.

## Adding a New Platform

To add a platform such as macOS or Android, the intended workflow is:

1. Extend detection heuristics in `evidence_platforms.py`.
2. Add platform metadata to `PLATFORM_REGISTRY`.
3. Register artifact families in `artifact_registry.py`.
4. Add parser plugins and normalizers.
5. Expose any platform-specific enrichment during ingest.
6. Reuse existing UI through `platform_profile` and the frontend registries.

The goal is to register a platform and its families, not to add new `if linux` / `if windows` branches across multiple screens.
