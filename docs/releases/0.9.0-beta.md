# Kairon DFIR 0.9.0-beta

## Overview

Kairon DFIR 0.9.0-beta consolidates evidence intake, centralizes host resolution, and promotes Linux evidence to first-class support. The release focuses on deterministic host assignment, safer provenance, and consistent behavior across upload, register-path, Velociraptor, memory, disk-image, and reassignment workflows.

## Evidence Intake

- Host resolution is deterministic and policy-driven per evidence type.
- Explicit `host_id` is validated against the owning case before assignment.
- Explicit host names are normalized and matched case-insensitively before creating a host.
- Detected hostnames are normalized before reuse or creation.
- Auto Assign is available only where the evidence policy supports it and the candidate is unambiguous.
- Host ownership validation is centralized.
- Hostname variants such as case differences and trailing dots resolve to the same canonical host.
- Host assignment provenance and custody events are recorded when evidence is assigned or a host is created.

## Memory

- Memory wizard and legacy memory upload paths now use the same canonical host assignment behavior.
- Memory evidence requires an explicit source host.
- Memory Auto Assign remains disabled.
- Existing structured memory host errors are preserved for the wizard contract.

## Linux

- Linux triage collections are supported as uploaded archives and folders when they contain recognizable Linux artifacts.
- Linux disk images are supported through the disk-image intake path with read-only inspection and platform detection.
- Hostname detection supports common Linux metadata including `hostnamectl` and hostname files where present.
- OS/platform detection uses Linux collection and filesystem metadata such as `os-release`.
- Linux collection inventory covers journal exports, auth/syslog, cron, package metadata, user/login metadata, services, network configuration, and process listings when present.
- Processing visibility includes detected Linux inventory, coverage, warnings, and final evidence state.

## Upgrade Notes

- Take a PostgreSQL, OpenSearch, and evidence storage backup before upgrading.
- Startup applies existing migrations through the normal migration runner and compatibility schema checks.
- Host Resolution Service v1 does not require a new schema migration; it uses existing host, alias, evidence assignment, platform, metadata, and custody tables/columns.
- Existing hosts and aliases are not merged automatically during upgrade.
- Existing evidence remains readable; new host resolution applies to new assignments and intake operations.
- Reindex is not required solely for Host Resolution. Reindex only if operators need historical OpenSearch documents to reflect newly assigned host metadata.
- Rollback after migrations requires restoring the pre-upgrade database, OpenSearch data or supported rebuild, and evidence storage backup.
