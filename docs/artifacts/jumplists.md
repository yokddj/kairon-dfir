# Jump Lists / JLECmd

## What Jump Lists are

Jump Lists are recent or frequent lists associated with an application in Windows. They usually reflect:

- recently opened documents
- folders or paths used from an app
- scripts or binaries opened
- user interaction with a specific application

## AutomaticDestinations vs CustomDestinations

- `AutomaticDestinations`: lists automatically generated by the application or by Windows.
- `CustomDestinations`: lists maintained by the application itself.

In this iteration Kairon DFIR:

- still supports the `JLECmd` CSV
- can now parse raw `.automaticDestinations-ms` from Velociraptor
- has partial support for `.customDestinations-ms`

## Why they are important in DFIR

They provide context on **actual usage per application**. They do not always prove execution, but they do help answer:

- what file the user opened
- from which application
- whether it was a document, script, or executable
- whether there were `UNC` network paths
- whether there were indications of USB or removable media

## What JLECmd provides

`JLECmd_Output.csv` allows extracting:

- `AppID` and application description
- `AppName` with fallback from a basic mapping of known AppIDs
- target paths and local paths
- `InteractionCount`
- relevant timestamps
- arguments and working directory
- volume, serial, and network
- `MachineID`
- `TargetMFTEntryNumber` / `TargetMFTSequenceNumber` when present

## What the raw parser provides

For `automaticDestinations-ms` the app attempts to:

- open the OLE/Compound File container
- detect the `DestList` stream
- enumerate `LNK`-type streams
- extract paths, arguments, working directory, timestamps, and volume/network metadata

For `customDestinations-ms` the app performs a partial scan of `ShellLink/LNK` structures. If it does not obtain useful entries, it preserves warnings and does not break ingestion.

## What AppID means

`AppID` identifies the application to which the Jump List belongs. If `JLECmd` provides a description (`AppIdDescription` or similar), the app uses it as the display name.

## What InteractionCount means

It is a signal of interaction or recurrence. It does not equate to confirmed execution, but it helps prioritize recent or repeated items.

## Which timestamps are important

The app uses this priority for `@timestamp`:

1. `TargetAccessed`
2. `LastAccessed`
3. `AccessedTime`
4. `TargetModified`
5. `LastModified`
6. `ModifiedTime`
7. `CreationTime`
8. `TrackerCreatedOn`
9. source file mtime

## Relationship with LNK

Both `LNK` and `Jump Lists` describe user interaction with Windows resources, but:

- `LNK` usually represents a specific shortcut
- `Jump Lists` add the **application context** and recent usage

## How the effective path is calculated

When a record has several paths, Kairon DFIR calculates:

- `jumplist.effective_path`
- `jumplist.effective_path_source`
- `jumplist.display_name`

Current priority:

1. `LocalPath`
2. `TargetPath`
3. `TargetIDAbsolutePath`
4. `CommonPath`
5. `NetworkPath`
6. `RelativePath`
7. `Path` / `FilePath` / `FullPath`

This avoids showing partial values like `Desktop\\` when a better real path exists.

If only a generic target such as `Desktop\\`, `Computer`, or `This PC` exists, the app tries not to treat it as a useful effective path. That case may be marked as `generic_target_path` or discarded as `low_value_record`.

## What it detects as relevant

The app flags as interesting:

- `\\host\share\...`
- `NetworkPath`, `NetName`, or `ShareName`
- `DriveType` that looks removable
- cloud sync folders (`OneDrive`, `Dropbox`, `Google Drive`, `Box`, `Mega`)
- sensitive user paths (`Downloads`, `Desktop`, `AppData`, `Temp`, `Users\\Public`, `ProgramData`)
- double extension
- arguments such as `powershell -enc`, `bypass`, `mshta`, `rundll32`, `regsvr32`

## Context vs suspicion

- a `user_writable_path` such as `Desktop`, `Documents`, or `Downloads` is **context**, not suspicion on its own
- a normal document such as `.txt`, `.docx`, `.xlsx`, `.pdf`, `.csv`, or `.log` in those paths remains `info` with low risk
- the app only promotes JumpLists to `suspicious` when there are also executables/scripts, double extension, suspicious keywords, suspicious arguments, or high-risk combinations such as `AppData\\Local\\Temp` + script/executable

## How to interpret raw timestamps

When the raw parser cannot extract a timestamp from the item and falls back to `source_file_mtime`:

- the time represents the modification of the JumpList file
- it may indicate that the JumpList was updated
- it does not necessarily equate to the exact time the user opened that item

That case is reflected in:

- `timestamp_precision = source_file_mtime`
- `jumplist.timestamp_interpretation`

## How it is used in the app

Today Jump Lists feed:

- `Search`
- `Artifact Explorer`
- `Investigation Timeline`
- Semi-automatic analysis

## What the semi-automatic analysis shows

### Opened files

- timestamp
- user
- application
- effective target
- interaction count

### Recent documents

- documents opened from an application
- user and application context

### Applications used

- app name
- app id
- user
- count
- last seen

### Recent files / downloaded files opened / deleted files opened

- recent items per application
- downloads later opened
- files later deleted or recycled
- correlation with `Shellbags`, `Recycle Bin`, `Browser`, `LNK`, and `MFT/USN`

## Parser status in Velociraptor

- `ready`: the raw file can be parsed directly
- `partial`: there is useful but incomplete support
- `detected_not_implemented`: detected but no raw parser available

In JumpLists:

- `automaticDestinations-ms` appears as `ready`
- `customDestinations-ms` may appear as `partial`

## When it is strong evidence

A JumpList entry gains value when it combines:

- a clear `effective_path`
- a clearly identified application (`app_name` / `app_id`)
- an item-specific timestamp, better than `source_file_mtime`
- correlation with `LNK`, `MFT/USN`, `Recycle Bin`, `Browser`, or `Shellbags`

### Opened scripts

If the target is `.ps1`, `.bat`, `.cmd`, `.js`, `.vbs`, or the arguments contain PowerShell/cmd, it is highlighted as `script_opened`.

### Network / USB paths

If the target is UNC or `DriveType` points to removable media, network or removable-media context is added.

## How it correlates with other artifacts

Kairon DFIR attempts a basic correlation when:

- the `effective_path` matches an `LNK`
- the parent folder matches `Shellbags`
- the same path appears in `Recycle Bin`
- it matches a `Browser download`
- the target matches a `4688`
- the target or its name matches Prefetch
- the target appears in `process.command_line`

## Current limitations

- A Jump List indicates recent use or interaction, not always confirmed execution.
- It may contain old entries.
- There is not always an explicit user; sometimes it is inferred from the path.
- A complete path does not always exist.
- `automaticDestinations-ms` can now be parsed raw, but `customDestinations-ms` remains partial.
- The `AppID -> application` mapping is useful but incomplete by design.
- If an `AppID` cannot be resolved, the app preserves the `app_id` and marks it as `unresolved_jumplist_app_id` as a data-quality flag.
- Some entries may be omitted as `low_value_record` if they do not provide an effective path, timestamp, or useful metadata.

## Common false positives

- legitimately opened documents
- corporate network paths
- scripts or binaries used by administrators
- old entries that no longer represent current activity
